# Assumptions that break under iterative, performance-motivated editing

**Status:** draft v2 (critic fixes applied), 2026-11-21.

**Why this file matters.** Our novelty lives here. Each row names an assumption a reduction technique relies on, cites where the literature states or tests it, and explains why it is at risk in our setting. Our setting is many small edits, each made to gain speed, each accepted after a reduced check, accumulating over a session, on Python code that may have C or Cython extensions.

**Evidence labels:** the *source* column is [R] read in source, [F] read through a web-fetch summary, or [A] abstract only. The *why it breaks* column is [I] inferred unless marked otherwise. Each assumption becomes a hypothesis W3 can measure (last column).

## A. Assumptions about a single edit, made worse by the edit's purpose

| # | Assumption | Where stated | Why it breaks for performance edits | Testable as |
|---|---|---|---|---|
| A1 | **Behaviour-preserving change: tests that do not traverse the change cannot change outcome** (controlled regression testing) | [R] rothermel1997safe §3.1.2 | Optimizations add shared state: caches, memoization, precomputed tables, lazy imports, object pools. A test that never reaches the new code can still see changed global state. NameRTS's two misses came from shared global state and an external callback [R WangPradelLiu2026 §4.2]. | Misses on edits classified as caching or global-state changes vs other edits |
| A2 | **The code that changed is code the selector can see** | [F] TestmonBlog (coverage.py limits); [R] ShiZhaoMarinov2019 §I (non-source files missed); [R] gligoric2015ekstazi §2 (external files) | Performance edits often move work into C, Cython or NumPy, or change build flags. coverage.py tracks Python lines. Neither testmon's nor coverage.py's docs mention native code [U], and Cython coverage needs a trace-enabled build [A]. PerfAgent's authors say native-extension regressions can slip through between iterations [W2: PerfAgent §VI]. | Share of edits touching non-Python files; misses among them |
| A3 | **Edits are local in time:** a benchmark that does not cover changed code is unaffected | [R] laaber2021tcp, mostafa2017perfranker (coverage/impact models) | Coverage is necessary but not sufficient [R ding2020readily §4]. Non-local effects include CPU caches, memory layout [R mytkowicz2009wrong; curtsinger2013stabilizer], allocator and GC pressure, import time and interpreter specialisation [I]. | Slowdowns injected into uncovered functions; layout-only control edits |
| A4 | **The goal is "no regression"** | RTS and batching literature throughout | Our oracle is two-sided. Each edit must *gain* speed on its target and lose none elsewhere. Chen & Shang find regressions often ride along with improvements, unnoticed even by developers who are optimizing [R chen2017exploratory §1]. A neutral result is a failure of the edit, not a pass. | Rate at which the reduced check falsely accepts edits that turn out neutral or slower |
| A5 | **Import-time and global code is rare in diffs** | NameRTS: changes to side-effecting functions run at import time select all tests (5 of 50 matplotlib commits); plain global-variable edits are modelled and do not [R WangPradelLiu2026 §3.1, §4.2]. Coverage-based RTS selects most tests for import-time code [R §1] | Precomputed tables, module-level caches and lazy imports are classic Python optimizations [I]. When such an edit runs code at import, or the selector is coverage-based, the reduced set collapses to the full set, so there is no saving. | Selection ratio by edit type |
| A6 | **Numerical output is stable** | Luo2014 lists floating point as a flakiness cause [R §3.1] | Vectorising, reordering reductions and changing dtype alter results within tolerance. Tests with thresholds may flip on rare inputs [I]. | Tolerance-flip rate on numeric edits |
| A7 | **The build flags and toolchain are fixed** | [R] mokhov2020buildsystems §8.3 (untracked deps such as compiler version); [F] distutils build_ext uses mtime only | Optimizations edit `-O`, `-march`, Cython directives and build options. A flags-only change may not trigger a rebuild under setuptools or Cython [F], so the binary under test is stale. A stale binary can produce a "speed-up" that is not real. | Injected flag-only edits: does the reduced build rebuild? |

## B. Assumptions that break because edits accumulate

| # | Assumption | Where stated | Why it breaks over many iterations | Testable as |
|---|---|---|---|---|
| B1 | **Dependency data is fresh:** recorded on the baseline the edit is applied to | [R] gligoric2015ekstazi §3.3 (collection only for executed tests), §5 (one observed run) | Reduced runs re-record only the tests they selected. Unselected tests' dependency maps age across edits. Each edit moves hot paths (inlining, helper extraction), so maps decay. Chittimalli & Harrold (TSE 2009) show that outdated coverage makes selection inaccurate for one version step [A]. No source measures misses as the refresh interval grows across several revisions (claim C7, partial). | Misses vs number of edits since the last full re-collection |
| B2 | **The profile or coverage used to select benchmarks is current** | [R] japke2025uoptime (configuration from an old run); [R] laaber2022searchbased (history); [A] alshoaibi2019price (rules "degrade over time") | Optimization changes the profile itself. That is its purpose. | Benchmark misses vs profile age |
| B3 | **Each check compares with the immediate parent** | asv `continuous`, pyperf `compare_to` [F] | Sub-threshold changes compound. asv's default factor is 1.1 [F]. Ten edits each 1% slower on a non-target benchmark pass every per-edit check. MongoDB's *earlier* threshold system compared with the previous run, a week-old run and the last stable release. It still listed "multiple small changes over time causing a drift down" as a failure mode, produced up to 99% false positives, and was replaced by change-point detection, which finds drift only after the fact [R daly2020changepoint §1–2]. A comparison with the original baseline therefore needs a noise-aware threshold (P6). | Cumulative slowdown against the *original* baseline that per-edit checks never flagged |
| B4 | **Each change fails or passes on its own** (single culprit, independence) | [R] najafi2019bisecting §2 (bisection); [R] zeller1999yesterday §1 (interference exists) | Later edits build on earlier ones. A fault can be introduced at edit i and exposed only at edit j, or masked by j. Probing "edit i alone" is meaningless, so the search must run over prefixes. Reverting edit i can make later edits unbuildable (dd's UNRESOLVED outcome) [R zeller1999yesterday §5]. | Interaction faults injected across two edits |
| B5 | **Failure probability per change is low and stable** | [A] beheshtian2022batch (benefit below 40% failure rate); [R] najafi2019bisecting §5 (best batch size shrinks as culprit rate rises) | Optimization concentrates edits in hot, risky code [I]. Risk per edit may rise during a session as easy wins run out. | Per-edit failure rate over session position |
| B6 | **The oracle is binary and deterministic** | [R] zeller1999yesterday (consistency); [R] henderson2023flake (exists because this fails) | Performance verdicts are noisy and not monotone [F asv find; A ocariza2022bisection]. Bisecting a checkpoint failure needs repeated measurements and can find no culprit at all (pure drift or environment). | Culprit-finding accuracy on injected slowdowns of decreasing size |
| B7 | **Build state matches the source** | [R] mokhov2020buildsystems §3.6 (per build) | Correctness is defined per build, not per sequence. Reverts and patch application can set mtimes older than the built artifact, so a timestamp-based rebuild skips work [I from F distutils/cython code]. Stale artifacts can survive many edits. | Clean-vs-incremental artifact comparison at each checkpoint |
| B8 | **The test suite is unchanged by the edits** | [R] zhao2022largescale §5: only 15% of performance fixes revise tests (13% in Python) | New fast paths (specialised branches) may be covered by no test at all. Coverage-based selection then selects nothing that reaches them [I]. | Coverage of new branches introduced by edits |
| B9 | **Flakiness is a fixed property of tests** | [R] Gruber2021; [R] Luo2014 | Caching edits create new state between tests, so new order dependencies appear. Deselecting a test can remove a state-setter [R Parry2021 §3.2 for victim/brittle; rest I]. | Outcome changes under reversed order at checkpoints |

## C. What this means for the design (inferred)

1. **The per-edit reduced check needs a guard that looks backward.** Two kinds of evidence are missing between full checks: the cumulative distance from the original baseline (B3), and the age of the dependency and profile data (B1, B2). A full check triggered by accumulated change is the natural response. No source evaluates such a trigger (see `beyond-literature-claims.md`, C1).
2. **The edit type predicts which assumption fails.** That is a deterministic routing signal:
   - native or build edits break A2/A7;
   - global or caching edits break A1/A5;
   - numeric edits break A6.
3. **Both a benchmark set and a test set have to be selected.** Ding et al. show the covering-tests set is a poor performance oracle [R]. The benchmark selection needs a fixed sentinel set as well as profile-based selection (A3, B3).
