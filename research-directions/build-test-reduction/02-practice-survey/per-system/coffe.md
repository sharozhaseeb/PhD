## 1. What it is
Python benchmark (398 function-level, 358 file-level problems) measuring efficiency of LLM-generated code using CPU instruction counts on LLM-generated "stressful" tests (STGen); metric efficient@k. [src paper §3, abstract]

## 2. Build / environment
- No compile step (Python); candidates run inside a Docker image built once (`docker build . -t coffe`); `-x` runs on host. [src README Installation]
- Code: one container per worker command, image tag `coffe`, bind-mounted workdir, `timeout` prefix. [src] coffe/sandbox.py:5-30.
- Paper says measurements run in Docker so that "only one single process is running" [src] paper §7.1, but the code launches `-n` parallel containers whenever `parallel_num > 1`, including for `instr_count`. [src] coffe/evaluate.py:197-215; README.md (pipeline `-n`). [inf] the one-process guarantee holds only with n<=1; instruction counts are less sensitive to co-running processes than wall time, but the guarantee is not enforced.

## 3. Correctness tests per candidate
- All original benchmark tests are used for correctness; ground truths validated against them first. [src] paper §3.1.1, §3.4 (not re-verified); coffe/evaluator.py:321 (`verify_groundtruth`), :439 (`verify_predictions`).
- Pipeline phases: sanitize -> compilable -> correctness -> instruction count -> metric; only predictions in `*PASSED_SOLUTIONS.json` are measured. [src] README.md (Usage/Pipeline); coffe/main.py:72,196-232.
- Correctness time limit per test = max(0.1 s, 10 x reference time); `fast_check` default True. [src] coffe/code_execution.py:603-615; coffe/evaluator.py:427.
- Fixed per problem; no per-edit selection. [inf]

## 4. Performance measurement per candidate
- Instruction count via Cirron `Collector` around the call (function-level: `fn(*input)`; file-level: `exec(code)` with stdin patched); needs `perf_event_paranoid` <= 2. [src] coffe/code_execution.py:26,327-339,751-754; coffe/main.py:34-40; README.md (Installation); paper §4.5.
- 12 repeats per stressful test, each repeat in a fresh `multiprocessing.Process` (random seed 1024); drop highest and lowest; mean of the remaining 10 (std ddof=1 kept). [src] coffe/code_execution.py:1012-1020, 764-782, 697; paper §3.4.
- Time cap: paper states 5 s per single measurement (§3.4). In code, `[5 for t in testcases]` is passed as `ref_time` and the limit is `max(0.1, 10 x ref_time)`, i.e. 50 s per run. [src] coffe/evaluator.py:946; coffe/code_execution.py:998-1006. [inf] paper/code mismatch (5 s vs 50 s); no other 5 s cap was found.
- 20 stressful tests generated by STGen, top 5 by average instruction count kept (paper §3.4). [src] paper §3.4. The repo ships the kept ~5 per problem (README stats table: 4.99 / 4.95 per instance); `stgen/st_generator.py:33` has `iteration = 20`, but a rank-by-instruction-count step was not found in `stgen/`. [unk] where top-5 selection is implemented.
- Metric: efficient@1 counts a correct sample if the SUM of instruction counts over the stressful tests is strictly less than the best ground truth's sum (`gt > sum(cic)`); speedup = sum(gt)/sum(candidate), over correct samples only. [src] coffe/evaluator.py:1317-1327 (efficient), :1273-1288 (speedup); paper §3.3.2 Eq. 3, §4.2.
- Stability claim: paper reports >1000x smaller RSD than execution time (RSD 0.003-0.005% vs 2.37-5.65%, Table 4; the critic's recomputation from those ranges gives ~470-1,900x), on repeated runs of ground-truth solutions on correctness tests, one machine, stressful tests excluded. [src] paper §5.1, Table 4.
- No statistical test; one fixed threshold (strictly fewer instructions than the best ground truth). [src] coffe/evaluator.py:1324.

## 5. Cost per candidate
- [unk] no per-candidate time. Paper bound: a test case takes at most ~1 minute (12 x 5 s) [src] paper §3.4; with the code's 50 s limit the worst case would be larger. [inf]

## 6. Iteration / cumulative re-validation
- Single-shot sampling, no iteration or accumulation; each prediction is scored independently against the best ground truth. [src] coffe/evaluator.py:1292-1336.

## 7. Limitations stated
- Instruction counts still affected by optimisation techniques; baselines only GPT-4o; Python only; repo-level generation excluded "because of measurement difficulty"; absolute counts machine dependent. [src] paper §7.1 (optimisation techniques may affect counts; baselines GPT-4o), §7.2 (Python only), §2 (repo-level excluded: modules and third-party dependencies); no standalone limitations section.
