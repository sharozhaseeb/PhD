## 4. Performance measurement per candidate
- Workloads: one human-written (author-annotated) workload script per task, peer-reviewed and validated on base and patched commits; about 200 author-hours for 1,041 candidate instances. [src] paper Sec. 2.1 Stage IV, App. E.4 (fetch summary); `README.md:132-135`. LM-generated workloads appear only as a side study (Sec. 4.2).
- Repeats/statistics: workloads use `timeit.repeat`; annotator template `number=1, repeat=10`; one raw example `number=5, repeat=1000`; no universal in-workload warm-up policy (each workload keeps the expert's). [src] paper App. B.2, C, E.4 (PDF text: templates `repeat=10`; example `number=5, repeat=1000`). The grader parses printed "Mean:" and "Std Dev:" values. [src] `H/test_spec.py:1157-1182`. HARNESS-level warm-up: the whole `perf.sh` is run once unmeasured before the pre-edit and again before the post-edit measurement (`perf_warmup=True`). [src] `run_validation.py:560-572, 636-650`. With `process_isolation=True` (CLI default) the workload is AST-rewritten so each `timeit` repeat runs in a freshly forked child (defeats run-to-run caching). [src] `run_validation.py:522-532`, `H/run_to_run_isolation.py:220-250`, paper App. L.2.
- Pre-edit runtime is re-measured for every candidate in its own container, then post-edit (CLI path: `run_validation.py:540-730`; legacy: `run_evaluation.py:157-178, 251-272`). The gold run is a separate evaluation run. [src] `scripts/eval/README.md:8-14`. SR uses `before_mean/after_mean` from `perf_summary.txt` (`run_validation.py:700-730`, `report.py:60-100`). No statistical test or variance-based acceptance at evaluation time; SD is recorded but unused in SR. [src]
- Speedup Ratio = (T_pre/T_post_LM)/(T_pre/T_post_gold); aggregated by harmonic mean with a per-instance floor 0.001. [src] `report.py:83-99, 140-149, 180-184`; `README.md:141-153`.
- Code oddity in LEGACY `run_evaluation.py` only: `improvement` is computed from `post_edit_perf_runtime` (wall time of perf.sh, which includes install), not the parsed post-edit mean. [src] `H/run_evaluation.py:274-276`. The CLI path computes `improvement = pre_mean / post_mean` (`run_validation.py:~716`) and reports use `perf_summary.txt` (`report.py:80-97`), so harmless. [src]
- Curation filter: workload dropped if mean_pre - mean_post <= 2*sigma_post (heuristic, not a formal test). [src] paper App. E.5 (PDF text).
- Noise control: 4 vCPUs (whole physical cores, no sibling sharing) and 16 GB per worker, NUMA-bound; Docker/containerd daemons pinned to separate cores; one n2-standard-64 VM, 12 workers recommended. [src] paper Sec. 3, App. F.2; `README.md:39, 66, 184`; `H/cpu_assignment.py:73-84`. Reported SR spread under 0.5% over three runs (Table 11). [src] paper App. N. Docker-daemon pinning is described in the paper only; `scripts/vm/` not read. [unk]

## 6. Iteration / cumulative re-validation
- Single patch per instance (pass@1). [src] paper Sec. 6 (limitations).
- Within the agent loop the agent can run its own tests and benchmarks, but the harness evaluates only the final patch. [inf]
- No cumulative re-validation: one correctness run and one post-edit perf run for the final patch. [src] `run_validation.py:636-1010`.

## 7. Limitations the authors state
- Mainly Python/Cython; extending to C/C++/Rust would need changes to test selection and build handling. [src] paper Sec. 6.
- Longer-running workloads, non-CPU hardware, and memory+runtime multi-objective evaluation not covered; pass@1 only. [src] paper Sec. 6.
- Observed workload overfitting and semantic drift (e.g. returning the input unchanged). [src] paper Sec. 4.2.

## 8. Relevance to Study 1 (reduced build + reduced test/benchmark per edit, deterministic)
- Closest existing practice to test reduction, but the reduction is per task and derived from the expert diff (coverage over thousands of tests), not per candidate edit. A per-edit selector would be new relative to it. [src] paper App. E.3; `test_spec.py:521-523`; [inf]
- Every candidate pays full reinstall(s) (`specs["install"]`, 5x on the CLI path) + covering tests + workload; no build reduction in the harness, so it is a direct baseline for build-cost measurement. [src] `test_spec.py:490-491`, `run_validation.py:540-1010`.
- Strong noise controls (whole-core pinning, NUMA, fixed VM, under 0.5% SR spread) define the timing-oracle bar a deterministic metric must be compared against. [src] paper App. F.2, N.
- One workload per task, separate from tests; the only benchmark-side reduction knob visible is repeat count (`repeat=10` template). [src] paper App. C; [inf]
